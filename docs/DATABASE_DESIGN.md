# Database Design — Agently

PostgreSQL 16+ (developed on 18), SQLAlchemy 2.x models, Alembic migrations. Models live in `backend/app/modules/<module>/models.py`; `backend/app/models.py` imports them all for Alembic. Planning rationale: `docs/plans/2026-11-21-1341-feat-database-and-migrations-plan.md`.

## Conventions

- **Primary keys:** UUIDs on every table, generated by PostgreSQL (`gen_random_uuid()`) with a Python-side default. IDs that appear in URLs are not guessable.
- **Timestamps:** every timestamp column is `timestamptz`. `created_at` defaults to `now()` in the database. `updated_at` is set on insert and refreshed by the ORM on update. There is no trigger, so a raw SQL `UPDATE` does not refresh it.
- **Constraint names** follow a fixed convention (`pk_`, `fk_`, `uq_`, `ix_`, `ck_`), so migrations can refer to them reliably.
- **Every schema change is an Alembic migration.** Never edit the database by hand.

## Tables

| Table | Purpose | Key rules |
|---|---|---|
| `users` | Accounts | `email` unique regardless of case (unique index on `lower(email)`); stored as entered, so lookups must compare `lower(email) = lower(:input)`. `password_hash` is Argon2id (ADR-0003); never the raw password. |
| `workspaces` | Tenants | `name` required. |
| `memberships` | A user's role in a workspace | One per `(user_id, workspace_id)`. `role` is `owner` or `member` (check constraint, so adding a role later is a constraint swap, not an enum migration). A user can belong to many workspaces. |
| `sessions` | Server-side login sessions (ADR-0003) | Stores only `token_hash`, unique and indexed; never the raw token. `expires_at` required, `revoked_at` nullable (set by logout). |
| `auth_throttle_events` | Counted login and signup attempts | One row per attempt and limit. `key_hash` is a SHA-256 of the scope plus normalised email and/or IP; no plaintext email. `created_at` is set by the application. Rows older than the longest throttle window are deleted whenever a new attempt is recorded, so the table stays bounded. Not linked to `users`: unknown emails are counted too. |

## Deletion behaviour (PRD DATA-1)

Deletion is a **hard delete**. Rows are removed immediately: there are no `deleted_at` columns and no purge job. The database enforces the cascades with `ON DELETE CASCADE`, so they hold for ORM deletes and raw SQL alike:

- Deleting a **workspace** deletes its memberships. Its users remain.
- Deleting a **user** deletes their sessions and memberships. The workspaces they belonged to remain.

**Known gap (Slice 1.3):** deleting the account of a workspace's last owner leaves that workspace with no owner. Slice 1.3 must prevent the last owner from leaving the workspace or deleting their account. Until then, avoid that operation.

Later tables (agents, conversations, memories, knowledge sources) will document their deletion behaviour here when they are added.

## Migration workflow (from `backend/`)

```powershell
.venv\Scripts\alembic upgrade head        # apply all migrations
.venv\Scripts\alembic downgrade -1        # roll back one revision
.venv\Scripts\alembic revision --autogenerate -m "describe change"   # then hand-review the file
.venv\Scripts\alembic check               # fails if models and migrations have drifted
```

Alembic reads the database URL from `DATABASE_URL` (environment or `backend/.env`), never from `alembic.ini`.

## Tests

- DB tests create `agently_test` themselves: it is dropped and recreated at the start of every run, migrated to head, and dropped at the end. Each migration test gets a fresh `agently_migrations_scratch`.
- The helpers refuse to create or drop any database whose name doesn't end in `_test` or `_scratch`, so the dev `agently` database can't be dropped by the test suite.
- Without `DATABASE_URL`, DB tests are skipped, and pytest ends with a line like `21 database tests SKIPPED: DATABASE_URL not set`. A skip is not a pass.
